## Purpose

Prepare explicit role-and-resource access rules for five independent demo actors:
- **seller** — own vehicle intake, submit, own watermarked preview;
- **admin** — same isolated demo's approval, lot and auction operations, permitted audit;
- **mitko** — own bidder acceptance, bid, allowed document preview;
- **borko** — separate bidder with NO access to Mitko's resources;
- **automation** — read-only demo audit foundation; no winner selection, release, payment or real effects.

Each actor has a unique demo-only subject ID and session ID; duplicate roles, IDs and sessions are rejected. The role roster requires an actually issued MISSION-002 boundary, not a forged JSON object. Role checks are deterministic, fail closed on unrecognized actions, wrong scope, mismatched session, cross-bidder access and non-watermarked documents. Tests are offline with fixtures.

## 2026-10-30 incremental implementation — signed session verification

The next implementation slice adds `packages/domain/src/closed-demo-session-guard.ts` and the server-only adapter `app/lib/enchev-closed-demo-auth-server.ts` without exposing a route or touching production.

- HMAC-SHA256 signed, audience/namespace-bound ticket; maximum 15-minute validity; only isolated MISSION-002 boundaries may issue/verify.
- Cryptographic signature comparison is constant-time; malformed, wrong-key, altered, expired, cross-project or fake-boundary tickets fail closed.
- The server-side authorization contract reads **current** session and five-role roster from an injected trusted authority (no request-supplied role), checks active status and expiration, then applies ownership and action rules.
- Revoked sessions, unavailable authority, roster/session disagreement, role spoofing, invalid resource scope, non-watermarked documents and cross-bidder access are explicitly denied in isolated fixtures.
- Browser adapter loads the signing key only from server-side `ENCHEV_CLOSED_DEMO_SESSION_SECRET_BASE64URL`, requiring canonical base64url encoding of at least 32 securely generated bytes. This is a prospective preview-only setting; **no key has been created or deployed**.
- No external Supabase session adapter, live authentication, real server route, issuance endpoint, session store or browser login is supplied. The fake authority in CI is test-only. An active system cannot be inferred from these tests.

Workflow: `ENCHEV CLOSED DEMO MISSION-003 roles (policy only)`; the verifier `scripts/verify-enchev-closed-demo-session-guard.mjs` compiles and tests isolated signed-session cases. Its results alone can only prove this policy foundation, not GREEN for MISSION-003.

## Critical trust limitation

**This is NOT a login system and is NOT production authorization.** A caller could submit an alleged subject/session ID unless a separate server API verifies it. The current change does not expose an API, issue a cookie, read an OAuth provider, perform KYC, or grant database access. These fixtures cannot prove role ownership, prevent credential theft, or validate session expiry. It is an isolated authorization *policy foundation*, not MISSION-003 GREEN.

Existing [Etap 1 QA PR #377](https://github.com/SoulFlameAdmin/enchev-auctions/pull/377) contains a separate demo session design. Reuse or reconcile the server-side signature checks and authoritative session store in a reviewed integration PR; never accept user-submitted role claims as authority.
